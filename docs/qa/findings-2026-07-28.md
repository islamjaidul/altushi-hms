# QA findings — 2026-07-28

First run of the patient-lifecycle suite (spec 0028). Findings are ordered by what I would fix
first. Every one was reproduced against a running app; where a claim is structural rather than
executed, it says so.

**Environments.** Local: native `Hms.Web` (Debug) on `localhost:5199` against `hms-dev-db`,
a used database (49 patients, 104 invoices). Production: `https://hms.specshipper.com`,
**read-only probes only** — nothing was written there.

**Verdict.** The application itself held up well: all twelve roles behave correctly on local,
768 route-authorization assertions pass, and nine of the eleven existing threads pass. The
serious findings are in the **deployment's role grants** and in the **test harness**, not in the
product logic.

---

## F1 — Production role grants have drifted from the code · **High**

`rasel` (Billing Operator) can reach `/admin/approvals` on production. That page is
`[Authorize(Policy = Perm.AdminApprovalsDecide)]`, so reaching it means holding the permission.

**This breaks separation of duties on the money path**: the operator who requests a discount or
a refund can approve it. Locally the same user is correctly refused.

`admin` on production can reach **30 routes beyond its granted set** — billing, pharmacy, LIS,
diagnostics, registration, the dashboard. It is effectively a superuser. Locally it is refused
all thirty.

| user | role | extra routes reachable — production | local |
|---|---|---|---|
| `rasel` | Billing Operator | 1 — `/admin/approvals` | 0 |
| `admin` | Admin | 30 | 0 |
| other 10 | — | 0 | 0 |

**Cause.** `src/Hms.Web/DevSeed.cs:114-119` seeds permissions **additively**: it inserts a grant
if absent and never removes one. A permission granted by an older build, or added by hand at
`/admin/users`, survives every subsequent deploy. Nothing anywhere compares a deployment's
grants against the code's matrix.

**Fix.** Two parts, and the first is urgent on its own: revoke `admin.approvals.decide` from
Billing Operator on production and audit what else the Admin role carries. Then decide whether
`DevSeed` should reconcile (remove grants no longer in `Roles`) or whether drift detection
belongs in the suite — reconciling silently would be its own hazard on a customer database, so
a reported diff is probably the right answer. Tracked as `LC-XCUT-14`.

**Caveat.** Production is still a demo instance (`HMS_SEED=true`, `Demo#1234` live), so this is
not yet patient data. The drift *mechanism* is what outlives the demo.

## F2 — `appointments.create` is declared, granted, and enforced nowhere · **High**

| Where | What |
|---|---|
| `src/Hms.Web/Perm.cs:16` | declares `appointments.create` |
| `src/Hms.Web/DevSeed.cs:22` | grants it to Receptionist |
| everywhere else | **no reference at all** |

`/appointments` carries only `[Authorize(Policy = Perm.AppointmentsRead)]`
(`Pages/Appointments/Index.cshtml.cs:21`), and neither `OnPostIssueAsync` (`:88`) nor
`OnPostAdvanceAsync` (`:128`) adds a check. **`appointments.read` alone can issue and advance
serials.**

Not exploitable by any seeded role today — the Receptionist holds both — so this is structural,
not executed. It matters because the §12 role matrix is editable data at `/admin/users`: grant
someone read-only access to the queue and they silently get write. Given F1 shows grants
*do* drift in practice, the latent case is not theoretical.

Contrast the correct pattern at `Pages/Lis/Board.cshtml.cs:43`, where a shared screen splits by
role: `private bool CanHandleSamples => Can("lis.sample.collect")`, checked in each handler.
That is why `lis.sample.collect` also has no `[Authorize]` and is nonetheless enforced — I
verified it by having `chowdhury` POST the collect handler and be refused.

**Fix.** Add `if (!Can("appointments.create")) return Forbid();` to both handlers, matching the
LIS pattern. Tracked as `LC-QUE-08`. The new traceability guard carries it as a documented
exception; remove it from `KNOWN_UNENFORCED` once fixed.

## F3 — The t1 suite exhausts its own fixtures and cannot be re-run · **High**

Three of nine threads fail on a database that has simply been used a few times. All three share
one cause: finite seeded fixtures are consumed and never returned.

| Thread | Failure | Fixture state |
|---|---|---|
| `ipd-thread.py` | `✗ a free cabin is on offer` | Cabin Block **3/3 occupied** |
| `pharmacy-thread.py` | crash, see F4 | Seclo **0 on hand** |
| `ot-thread.py` | `✗ the consumable is recorded against the case` | Moxacil **0 on hand** |

```
 Cabin Block            occupied  3        Moxacil  0
 General Ward (Female)  occupied  4        Seclo    0
 General Ward (Male)    free      4        Fexo     22
 ICU                    free      2        Napa     589
```

Every one of these passed when run individually earlier today, and failed on the second pass.
`ipd-thread.py` has a housekeeping step 14 that hands beds back, but it releases general-ward
beds only — the cabin taken by the transfer test (step 10) is never released.

This matters beyond convenience. The scripts' docstrings claim dirty-database tolerance, the CI
`upgrade-path` job runs nine of them against restored production-shaped data, and
`eng/verify/README.md` presents them as repeatable. As written they degrade with every run
until the gate goes red for reasons that have nothing to do with the build. Spec 0020's notes
record this exact regression being fixed once before — it has come back.

**Fix.** Each thread should return what it takes: release the cabin, and either replenish stock
or assert the FEFO/expiry *property* against a batch it created itself (which is how
`pharmacy-thread` step 3 was already fixed once). A cheap interim guard: fail with a clear
"fixture exhausted, reset the database" message rather than a bare assertion.

## F4 — `pharmacy-thread.py` crashes instead of failing · **Medium**

```
File "eng/verify/pharmacy-thread.py", line 140
    pos = ph.post("/pharmacy/pos?handler=Add", {"productId": seclo.group(1), ...})
AttributeError: 'NoneType' object has no attribute 'group'
```

The POS type-ahead lists only products with sellable stock; Seclo is at zero, the regex matches
nothing, and `.group()` is called on `None`. The operator-facing message is
`'NoneType' object has no attribute 'group'`, which says nothing about what broke.

**Fix.** Guard the match and fail the check with the reason — the same treatment the other
threads give a missing fixture.

## F5 — Eleven of sixty-four protected routes are never loaded by any UI test · **High**

`eng/verify/ui/helpers/users.ts` lists 55 routes; the app protects 64. The missing eleven are
disproportionately the consequential ones:

```
/ipd/folio/{id}        /ipd/discharge/{id}    /emr/consult/{id}
/emr/prescription/{id} /radiology/report/{id} /radiology/print/{id}
/ot/case/{id}          /lis/amend             /diagnostics/order/{id}
/admin/sms             /admin/templates
```

These are the money- and clinically-critical detail screens — the folio, the discharge gate, the
prescription, the signed report, the amend path. The Playwright tables are hand-synced with
`DevSeed.cs`, `Perm.cs` and `ModuleNav.cs`, so the omission is silent.

**Fix.** Add the eleven to `ROUTES`. `eng/check-lifecycle-traceability.sh` now re-extracts every
`@page` route and its `[Authorize]` attribute from source and fails on drift, so this class of
omission is caught from here on. Tracked as `LC-XCUT-13`.

## F6 — `nav-smoke.sh` cannot fail · **Medium**

The script has no exit-code logic and treats `302` as acceptable
(`eng/verify/nav-smoke.sh:17`). Denial in this app **is** a 302, to `/denied`:

```
$ bash eng/verify/nav-smoke.sh md 'Demo#1234' /registration /billing/opd
exit code: 0        # md holds neither permission; both were refused
```

A permission regression that redirects an entire role to `/denied` produces a clean-looking
table and a zero exit. The script is used in the CI `upgrade-path` job across 13 user/route
batches.

**Fix.** Follow the redirect, treat a `/denied` target as failure, and exit non-zero. The new
`_harness.py` already does this — `Session.denied()` distinguishes a refusal from an ordinary
redirect, which is the distinction the whole authorization suite rests on.

## What passed

Worth stating, because it is most of the system.

- **Authorization on local is correct.** 12 roles × 64 protected routes, both directions —
  every granted route reachable, every ungranted route refused. 768 assertions, zero failures.
- **Separation of duties holds where it is enforced.** `ripon` cannot verify the result he
  entered; `moinul` cannot report the study he performed; `nasrin` cannot write a prescription;
  `shahid` cannot settle a discharge. Verified at the handler, not just the hidden button.
- **`/dashboard` is genuinely MD-only** — eleven roles refused, one allowed.
- **Anonymous surfaces leak nothing** — `/login`, `/public/queue`, `/public/report-status`,
  `/health` answer; everything else redirects to login.
- **Nine of eleven threads pass**, covering the money spine, the IPD folio and discharge gate,
  EMR sign-and-correct, OT state machine, radiology e-sign, pharmacy FEFO and expiry, the
  terminal exits (death, absconded) and double-submit.
- `golden-thread.py` fails **only** on its absolute-total assertion (`golden-thread.py:206`
  requires the dashboard to read exactly ৳550), which is correct behaviour on a used database
  and is exactly why it is tier t2.
