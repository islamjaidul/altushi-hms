# PRD §5 Requirement-Traceability Matrix — 15 Built Modules

Spec 0038 (full QA audit). Built by reading code only; the app was not run and the database was not touched.

**Verdict labels**

| Label | Meaning |
|---|---|
| `DONE` | Implemented; route and file named |
| `PARTIAL` | Partially implemented; the note says precisely what is missing |
| `ABSENT` | No code implements it |
| `UNENFORCED` | The data/field exists and is displayed, but the rule is never applied |

Modules M12, M13, M14, M15, M17, M18, M19 are excluded — no code exists for them.

## Cross-cutting findings

These sit under no single module but change how several verdicts above should be read.

1. **There is no background worker. `JobQueue` has zero callers.** `src/Hms.Kernel/Jobs/JobQueue.cs` is fully implemented (Postgres `FOR UPDATE SKIP LOCKED`, lease timeout, retry with backoff, poison parking) and registered in DI in both hosts — but **nothing anywhere calls `Enqueue`, and no `BackgroundService`/`IHostedService` exists to drain it**. Everything that ought to be scheduled therefore does not happen: bed-charge accrual (M6, lazy on folio view instead), approval escalation (M21), the end-of-day digest (M22), due reminders (M20), and SMS delivery. Any requirement whose verb is "automatically" or "daily" should be assumed unimplemented.

2. **Both "barcodes" in the product are decorative CSS, not symbology.** The patient ID card (M1) and the lab sample label (M8) both render `<div class="barcode">`, which resolves to a static `repeating-linear-gradient` in `src/Hms.Shell/wwwroot/css/app.css:843-848` — byte-identical on every document and encoding nothing. `src/Hms.Shell/wwwroot/js/barcode.js` is a scanner-*wedge input* listener only. So the scan-driven workflows the PRD specifies (card scan at registration, tube scan at collection) cannot work end to end with printed output, and the M1 scan route is additionally mis-keyed (`P` prefix vs. `ALT-` UHIDs).

3. **Server-side PDF is a spike, not a feature.** `src/Hms.Kernel/Printing/PdfRenderer.cs` contains only `RenderBanglaSpikeDocument` — the ADR-0014 font-shaping test. Every printable document in the product is browser print of HTML (`_PrintTools` partial), whose own comment says the server-rendered PDF path "is still to come".

4. **Reversal does not propagate out of Billing.** Cancelling or refunding an invoice correctly reverses the money, but leaves the downstream work order alive: a refunded diagnostic order stays `in_progress` on the lab board and the radiology worklist (M8), and `RestockAsync` restocks 100% of the goods on a *partial*-value refund (M11).

5. **`diag.test_order` never reaches `reported`.** No writer for `TestOrderState.Reported` exists anywhere. The public no-login page `/public/report-status` therefore shows "In progress" for a fully verified report sitting on the delivery counter, until someone physically hands it over.

6. **The HR SKU depends on seed data for its own configuration.** Pay structures, payroll policies (`DeductionRule`, `GraceTimeRule`, `OvertimeRule`, `PfPolicy`, `TaxSlab`), `PayComponent.ComputedKind`, `LeavePolicy`, and `Employee.UserRef` are all written **only** by `HrDemoSeed`/`HrSeed`. On a real install none of them can be created through any screen, so payroll cannot compute a line, leave entitlement is always zero, and no user can reach `/hr/me`. This is the single largest gap between "works in the demo" and "works for a customer".

7. **Page-level authorization is clean.** Every `.cshtml.cs` in `src/` carries an `[Authorize]` policy except Login, Logout, Denied, Index and the two deliberately public `/public/*` pages, and a fallback policy covers the rest. Several handlers were confirmed to re-check permission server-side rather than only hiding a button (`/radiology/worklist`, `/hr/leave`, `/diagnostics/delivery`).

## Most significant [M] absences across the product

Ordered by how much they block a real sale or a real hospital day.

1. **M20 — there is no SMS gateway at all.** No HTTP sender exists in `src/`, only 3 of 9 required triggers are wired, templates cannot be added, and delivery status is never written. Setting `HMS_SMS_MODE=live` silently stops SMS entirely rather than sending it. Notification is a headline PRD module and today it is a simulator.
2. **M16 — biometric attendance has no input path whatsoever.** `IPunchSource` has zero implementations, `ImportAsync` and `DeriveDayAsync` have zero callers, and there is no device connector *and no file-import screen*. Attendance rows exist only where a demo seeder fabricated them, so payroll on a real install has nothing to read.
3. **M16 — no pay structure, policy or payslip UI.** Payroll's computation engine is written but unreachable: no screen sets an employee's pay, creates any of the five policy types, or sets `ComputedKind`; and although the `Payslip` table exists, **no code ever inserts, reads or prints one**. There is no salary sheet screen either.
4. **M21 — the approval engine notifies nobody, and escalation never fires.** A bill held for a supervisor's discount approval waits until someone happens to open `/admin/approvals`. `EscalationMinutes` is captured and stored but no code acts on it, and no worker exists that could.
5. **M6 — certificates are numbered, audited and unprintable.** Discharge, death and birth certificates get gapless sequential numbers and reprint audit, but the frozen document body is never rendered — the "Reprint" button only increments a counter. A statutory document the hospital must hand over cannot be produced.
6. **M8 — order cancellation does not exist at the order level.** Nothing writes `TestOrderState.Cancelled`; a refunded or cancelled test keeps flowing through the lab and radiology worklists.
7. **M3 — appointments can only be created and cancelled.** Modify, postpone and transfer are all absent, no reason is captured for any state change, cancellation writes no audit row, and future-dated (phone) booking is impossible because the screen hardcodes today.
8. **M3 — doctor capacity is UNENFORCED.** `MaxSerials` is configured and displayed as "Capacity" but never compared to the issued count, so a 40-serial doctor silently gets a 41st.
9. **M9 — no separation of duty on result verification, and an amended report can become unsignable.** One person can both enter and sign a result (the seeded `Pathologist` role holds both permissions), and an amendment to an already-delivered order never re-enters the Verify worklist, so v2 can never be signed.
10. **M21 — audit misses the clinical modules and "from where".** LIS result entry/verify/amend, diagnostics order creation, appointments and doctor/referrer master edits write **no audit row at all**, and no audit record anywhere captures IP or host — both explicit PRD requirements.
11. **M22 — the MD dashboard has no IPD data and no date range.** No admitted/discharged/current counts, no bed occupancy, no refunds tile, no money-receipt counts, and the whole page is hardcoded to today.
12. **M6 — bed charges accrue lazily, not nightly.** Catch-up runs only when a suitably-permissioned user opens the folio, or at settlement. A folio nobody opens accrues nothing, and there is no proration on a transfer day.
